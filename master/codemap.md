# master/

## Responsibility

The `master/` directory is the FastAPI backend for Vigile, a zero-trust fleet management server. It serves as the central control plane: authenticates human operators via JWT, manages Worker node lifecycles through a strict state machine (PENDING to REVOKED), orchestrates Ed25519-based enrollment handshakes over WebSocket, dispatches approved intents to connected Workers, persists all state in SQLite, maintains an append-only SHA256 audit chain, provides LLM-powered chat with human-in-the-loop action proposals, and enforces rate limiting and RBAC at every endpoint.

## Design

- **Async-first FastAPI**: single-process asyncio application using `asyncio.Lock` for all shared state (node registry, pending intents, audit writes, rate limiter buckets). Lifespan context manager handles startup (DB init, migrations, SecurityManager init, plugin loading, heartbeat monitor) and shutdown in reverse order.
- **DI-at-the-edge**: `core/` classes receive configuration via constructor injection. No `core/` module reads `settings` or `os.getenv` directly. Config is wired in from `main.py` lifespan and `api/deps.py` at the FastAPI layer. This rule is documented but violated by `auth.py`, `nodes.py`, `worker_handler.py`, `database.py`, and `deps.py` which import `from master.config import settings` at module level.
- **No ORM, pure SQL**: all DDL lives in `db/models.py` as raw `CREATE TABLE` strings. Migrations are idempotent and run on every startup. `aiosqlite` with WAL mode, row factory, and a `transaction()` context manager wraps multi-statement operations.
- **Two-phase WebSocket protocol**: Phase 1 (enrollment) is a sequential challenge/response handshake with 30-second per-step timeout. Phase 2 (operational) is a long-lived bidirectional message loop for heartbeats, status reports, and intent dispatch. A 3x heartbeat-interval grace period detects dead connections.
- **Hook-based plugin system**: `PluginManager` replicates Pluggy's core pattern in ~240 lines of stdlib. Plugins in `plugins/` dropping a `.py` file with a `register(pm)` function auto-register at startup. Three hooks exist: `get_supported_actions`, `normalize_status_report`, `on_status_report`. Sync dispatch via `call()`/`call_first()`, async via `async_call()`/`async_call_first()`. Async hooks called via sync `call()` are silently skipped with a warning.
- **Intent-based Worker communication**: all remote operations (logs, stats, services, containers) follow the same pattern -- the API layer calls `NodeManager.send_intent()`, which stores an `asyncio.Future`, sends the intent JSON over the Worker's WebSocket, and awaits the future with a timeout. The operational loop in `worker_handler.py` resolves the future when `INTENT_RESULT` arrives.
- **SHA256 audit chain**: every state mutation calls `log_action()` which inserts an entry with `entry_hash = sha256(previous_hash | sequence | timestamp | action | user_id | node_id | details_json)`. The genesis entry uses `"0"*64` as previous hash. `verify_chain()` walks the full table and recomputes hashes to detect tampering. Writes are serialized via `asyncio.Lock` to prevent sequence collision.
- **Singleton DI pattern**: `SecurityManager` is explicitly initialized via `init_security()` call in the lifespan (one-time, raises if called twice). `NodeManager` and `PluginManager` are module-level singletons with empty constructors. `LLMClient` and `StructuredLLM` are lazily initialized on first `Depends()` call via module-level `None` sentinels in `deps.py`.
- **Settings auto-secret generation**: `config.py` uses `pydantic.BaseModel.model_post_init` to generate `secrets.token_hex(32)` for `SERVER_SECRET_KEY` and `JWT_SECRET_KEY` when env vars are empty. Safe for dev only -- production must set both explicitly.

## Flow

1. `uvicorn master.main:app` starts. FastAPI calls the `lifespan` async context manager.
2. Lifespan opens SQLite via `init_db()` (WAL mode, foreign keys ON, row factory), runs idempotent migrations (`run_migrations()` which creates all tables and seeds the `admin/admin` user if no users exist), initializes `SecurityManager` with server/JWT secrets and the Ed25519 master keypair (loaded from disk or generated), loads plugins from `plugins/` directory, and starts the `NodeManager` heartbeat monitor background task.
3. FastAPI registers four REST routers (`auth`, `nodes`, `services`, `chat`), the `/ws/worker/join` WebSocket route, admin debug endpoints, and three middleware layers (CORS, rate limiter, optional HTTPS enforcement).
4. A human operator authenticates via `POST /api/auth/login`. The `SecurityManager` verifies the bcrypt password, checks `is_active`, issues a JWT access token (1h default) and refresh token (24h default). The rate limiter applies 10 req/min on `/login`.
5. An admin generates a join token via `POST /api/nodes/generate-join`. This pre-creates a node in `PENDING` state, produces an HMAC-SHA256 signed `JOIN_TOKEN` (30-min TTL, single-use), stores its SHA256 hash in `join_tokens` table, and returns a `curl | sh` kickstart command.
6. The Worker downloads and runs `kickstart.sh`, which detects OS/arch, downloads the Go binary, verifies its SHA256, installs it, and starts it as a systemd service.
7. The Worker opens a WebSocket to `ws://master/ws/worker/join`. The `worker_join_handler()` function runs the two-phase protocol:
   - **Phase 1 (Enrollment)**: Worker sends `ENROLLMENT_REQUEST` with join token and Ed25519 public key. Master validates HMAC signature + TTL + IP prefix + DB consumption status, transitions node to `ENROLLING`, sends `ENROLLMENT_CHALLENGE` (32 random bytes). Worker signs with its Ed25519 private key and returns `ENROLLMENT_RESPONSE`. Master verifies the signature, atomically consumes the join token (via `UPDATE ... WHERE consumed=0`), stores Worker metadata (hostname, arch, OS, public key), generates a `WORKER_TOKEN` (JWT, 30-day TTL, 7-day rotation), transitions node to `CONNECTED`, registers the WebSocket in `NodeManager._connections`, and sends `ENROLLMENT_SUCCESS`.
   - **Phase 2 (Operational)**: a `while True` loop receives messages. `HEARTBEAT` (every 30s) triggers a timestamp update and `HEARTBEAT_ACK` reply. `INTENT_RESULT` resolves the pending future in `NodeManager._pending_intents`, unblocking the caller of `send_intent()`. `STATUS_REPORT` (every 60s) is normalized through the metrics plugin (validated via Pydantic `MetricsSnapshot`) and persisted to the `metrics_snapshots` table.
8. On disconnect, the handler unregisters the WebSocket connection, cleans up any pending intents for that node, and transitions the node to `RECONNECTING` (if it was `CONNECTED`) or back to `PENDING` (if enrollment failed).
9. The heartbeat monitor background task runs every 30 seconds. It checks all `ActiveConnection` entries: if `heartbeat_age > lost_threshold` (300s), it unregisters the connection and transitions to `LOST`. It then queries the DB for all `LOST` nodes: if `last_heartbeat > stale_threshold` (86400s), transitions to `STALE`.
10. An operator sends a chat message via `POST /api/chat`. The handler builds a system prompt with node context (name, state, OS, latest metrics), streams the LLM response via SSE, then attempts to extract a structured `ActionProposal` using `StructuredLLM` with Pydantic validation and retry logic. The proposal is persisted as `PENDING`.
11. An operator reviews and approves/rejects the proposal via `POST /api/chat/proposals/{id}/approve` or `/reject`. On approval, the proposal transitions to `APPROVED`, the intent is sent to the Worker via `NodeManager.send_intent()`, and the result transitions the proposal to `EXECUTED` or `FAILED`. All transitions are audited.
12. REST endpoints for services and containers (`GET /api/nodes/{id}/services`, `POST /containers/{id}/restart`, etc.) use the same `send_intent()` pattern with 15-second timeouts. The Worker Go binary dispatches to systemd or Docker and returns JSON results.

## Integration

- **Consumed by**: FastAPI server entrypoint (`uvicorn master.main:app`), integration tests (`tests/integration/test_api.py`), simulation scripts (`scripts/test_all_simulation.py`), the Go Worker binary (`worker/`) as the WebSocket peer. REST and WebSocket clients (frontend planned for Sprint 4).
- **Depends on**: `aiosqlite` (async SQLite), `fastapi` + `uvicorn` (HTTP/WS server), `python-jose[cryptography]` (JWT + Ed25519), `passlib[bcrypt]` (password hashing), `pydantic` (all models and validation), `httpx` (LLM HTTP client). Standard library: `asyncio`, `hashlib`, `hmac`, `secrets`, `base64`, `json`, `uuid`, `time`, `os`, `importlib`. The `cryptography` library (indirect, via python-jose) provides Ed25519 primitives. No `pydantic-settings`, no `openai` library, no SQL ORM, no pytest.
